## ADDED Requirements

### Requirement: 写操作乐观更新与失败回滚

系统 SHALL 支持写操作的乐观更新：在 mutation 发起时即时将预期结果应用到本地缓存并对用户可见，同时快照被修改查询的旧值。当 mutation 失败时，系统 MUST 用快照旧值回滚所有被乐观修改的缓存，并通过现有失败通知机制告知用户该操作未保存。乐观结果仅为本地预测，服务端 MUST 为最终权威。

#### Scenario: 乐观更新即时可见

- **WHEN** 用户提交新增/编辑/删除等写操作
- **THEN** 系统在请求往返完成前即时将预期结果应用到本地缓存并在 UI 反映，感知延迟接近 0

#### Scenario: 失败回滚到旧值

- **WHEN** 写操作的服务端请求失败
- **THEN** 系统将被乐观修改的查询缓存回滚到发起前的快照值，并显示失败通知条

#### Scenario: 成功后以服务端数据校准

- **WHEN** 写操作成功返回
- **THEN** 系统按统一失效映射重新校准相关查询，使最终展示与服务端数据一致

### Requirement: 乐观更新最终一致校准

系统 SHALL 在写操作结束（无论成功或失败）后，按统一失效映射（`MUTATION_INVALIDATES`）失效相关查询，确保乐观预测最终与服务端真实数据收敛一致。系统 MUST 在本地生成的临时标识与服务端返回的真实标识之间，通过该失效校准完成替换。

#### Scenario: 结束后统一失效校准

- **WHEN** 写操作进入结束阶段（settled）
- **THEN** 系统按 `MUTATION_INVALIDATES` 失效关联查询键，触发后台校准

#### Scenario: 临时 ID 被服务端真实 ID 替换

- **WHEN** 乐观新增使用了本地临时标识，且服务端成功创建记录
- **THEN** 失效校准后列表中的条目以服务端真实标识与数据为准，无重复或残留临时项

### Requirement: 乐观更新向后兼容

系统 SHALL 保持未配置乐观更新的写操作沿用既有的"成功后失效"行为，不得因引入乐观更新机制破坏现有写操作。

#### Scenario: 未配置乐观更新的写操作

- **WHEN** 某写操作未提供乐观更新器
- **THEN** 系统退化为成功后按映射失效的既有行为，功能不受影响
