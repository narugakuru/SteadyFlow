## Context

当前资产配置纪律在同一页面同时承载桌面表格、移动端卡片与类别内拖拽排序三类交互。现状问题集中在：

- 展开明细中金额为 0 的标的仍渲染，造成噪音与排序干扰。
- 移动端卡片把金额、盈亏、状态放在同一行，宽屏假设在 6 位以上金额下失效。
- 移动端拖拽完成后存在“回弹到原位”，说明本地状态与持久化结果之间有竞态或重置。
- 已部署版本进一步暴露出移动端触摸拖拽仍不可用：拖拽句柄所在区域没有明确阻止浏览器原生纵向平移，且排序列表位于底部弹窗与内部滚动容器内，导致触摸手势被滚动接管，表现为只能短距离位移、横向漂移，但不能稳定上下换位。

变更需保持桌面端布局与已有 API 契约稳定，优先在现有 capability 内做增量约束。

## Goals / Non-Goals

**Goals:**

- 明确纪律展开明细对 0 金额项的过滤与排序规则，减少无效信息。
- 在移动端采用三行堆叠布局，保证金额、盈亏、状态与调仓操作可读可操作。
- 修复移动端拖拽后顺序立即稳定且刷新后保持一致。
- 修复移动端触摸拖拽与滚动手势冲突，确保用户按住句柄后可以连续纵向移动多个位置完成排序。

**Non-Goals:**

- 不重做桌面端纪律表结构或视觉风格。
- 不引入新的拖拽库或大规模替换现有排序实现。
- 不新增数据库字段，仅基于现有排序字段与接口修复行为。

## Decisions

### Decision 1: 在纪律聚合层统一处理 0 金额项

在纪律展开数据构建阶段先过滤 `amount <= 0` 的明细项；若业务需要保留该项供统计，排序阶段将其稳定置于末位（次级按现有排序字段）。  
理由：把规则放在聚合层可同时约束桌面/移动端，避免前端重复实现和口径偏差。  
备选方案：仅前端隐藏。未采用原因是不同页面可能复用同一数据，前端隐藏会导致排序和计数不一致。

### Decision 2: 移动端资产类别卡片拆为三层信息

移动端卡片固定为：

- 第 1 行：标题 + 实际/目标进度信息
- 第 2 行：核心金额（大字号）
- 第 3 行：盈亏 + 状态，并在右侧放置调仓操作

理由：主数值优先级最高，状态和盈亏作为辅助信息；三层结构能容纳长数字并避免横向挤压。  
备选方案：维持单行并缩小字体。未采用原因是可读性下降且不同语言/币种长度不可控。

### Decision 3: 拖拽采用“本地顺序先落地 + 异步持久化 + 失败回滚”

在 `dragEnd` 后立即将本地列表更新为目标顺序，随后触发保存请求；请求成功保持现状，请求失败再回滚并提示。  
理由：回弹通常来自服务端刷新覆盖本地顺序；先落本地可保证交互连续性，再以持久化结果兜底一致性。  
备选方案：等待接口成功后再更新 UI。未采用原因是体感卡顿，且更容易出现“放手即跳回”的错觉。

### Decision 4: 仅让拖拽句柄接管触摸手势，并限制拖拽为纵向轴

在移动端排序弹窗中，仅对拖拽句柄应用显式触摸手势接管（例如 `touch-action: none`），避免浏览器把纵向移动解释为底部弹窗或内部列表滚动；同时对排序过程增加“仅纵向移动”的约束，消除横向漂移并提升目标命中稳定性。列表的非句柄区域继续保留正常滚动。  
理由：问题根因并非排序数据链路，而是触摸开始后事件所有权被原生滚动夺走。把手势限制在句柄区域可最小化对既有滚动体验的影响；限制纵向轴可使交互与“上下排序”的心智一致。  
备选方案：对整个弹窗或整行禁用触摸滚动。未采用原因是会让用户无法自然滚动长列表，副作用过大。

### Decision 5: 移动端拖拽修复同时覆盖 discipline 与 asset-class 两类排序弹窗

持仓排序弹窗与资产类别排序弹窗共用同一套 `dnd-kit` 传感器与句柄样式模式，因此修复策略应同步应用到两处，以避免一个弹窗修复后另一个仍复现同类问题。  
理由：两个弹窗当前都使用 `PointerSensor + TouchSensor`、可滚动容器和右侧句柄，属于同构问题。  
备选方案：只修 discipline 弹窗。未采用原因是会留下同类移动端缺陷，增加后续重复返工成本。

## Risks / Trade-offs

- [过滤规则改变可能影响“空仓位可见性”预期] → 仅对展开明细项生效，不影响类别汇总行与占比计算。
- [本地先更新顺序可能与服务端失败产生短暂不一致] → 增加失败回滚和错误提示，确保最终一致。
- [三行布局增加卡片高度] → 通过信息分层换取可读性，移动端滚动成本可接受。
- [拖拽句柄接管触摸手势后，用户可能误以为整行都可拖拽] → 在文案与视觉上持续强调“右侧句柄拖拽”，并保持句柄点击区域足够大。
- [底部弹窗与内部滚动容器存在双层滚动，仍可能影响边缘手势] → 仅在句柄区域禁用原生平移，并在真实设备上回归验证长列表拖拽与滚动切换。

## Migration Plan

1. 更新相关 capability delta specs，补充移动端触摸拖拽接管与纵向排序约束。
2. 前端实现移动端三行布局、拖拽状态机修复，以及句柄级触摸手势治理。
3. 后端/聚合层补充 0 金额过滤与末位排序。
4. 回归验证桌面端未受影响；移动端覆盖大金额、长列表滚动与真实触摸拖拽场景。

回滚策略：若线上出现异常，可回退本次前端布局与排序逻辑提交；必要时临时关闭移动端排序入口，仅保留桌面端排序能力，不涉及数据迁移。

## Open Questions

- 0 金额判断是否以绝对值阈值（例如 `< 0.005`）处理浮点噪声，或严格等于 0。
- 调仓按钮在移动端是否始终显示，还是仅在偏离非“正常”时显示。
- 是否需要在移动端排序弹窗中增加“按住右侧句柄拖拽”的明确提示文案。
- 真实设备回归阶段是否覆盖 iOS Safari 与 Android Chrome 两类浏览器，以验证 Pointer/Touch 事件兼容性。
