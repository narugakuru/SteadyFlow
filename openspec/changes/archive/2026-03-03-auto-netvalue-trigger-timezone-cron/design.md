## Context

当前净值记录逻辑分散在 Dashboard 页面的手动/加载触发中，资产写操作（账户、持仓、交易、批量更新）成功后不会统一刷新当日净值，容易出现净值与最新资产状态不一致。现有 netvalue 表已具备 `(userId, date)` 唯一约束，适合通过 upsert 实现“同日覆盖”。

本次变更还新增两项约束：

- 用户可手动设置净值时区，默认 `Asia/Shanghai`
- 每日自动记录一次，目标时间为用户本地凌晨 3:00

项目当前部署形态同时包含本地/离线运行与云端部署，方案需要兼顾：

- 接口内自动触发的低侵入改造
- 定时任务可在 Vercel 与本地环境都可运行（实现形式可不同，能力一致）

## Goals / Non-Goals

**Goals:**

- 移除 Dashboard 手动“记录净值”按钮，避免重复入口。
- 建立统一的净值记录服务与 mutation 包装器，避免在每个接口散落重复代码。
- 所有影响资产的写操作成功后自动刷新当日净值。
- 基于用户时区计算“当日”日期，默认 `Asia/Shanghai`。
- 提供每日自动记录能力，并保证在“本地凌晨 3:00”触发。

**Non-Goals:**

- 不引入“脏标记队列”或异步消息系统。
- 不改造 netvalue 历史展示结构与图表样式。
- 不新增额外数据库表（优先复用 settings）。

## Decisions

### 1) 抽取 `recordTodayNetvalue(userId, options)` 作为唯一净值写入口

- 决策：将 `POST /api/netvalue` 中的计算与写库逻辑下沉到 `src/lib/netvalue-service.ts`，API 与内部调用都复用该服务。
- 原因：避免净值计算逻辑重复；后续规则变更只改一处。
- 备选方案：继续只在 `/api/netvalue` 暴露 HTTP 调用（各 mutation 再 fetch 内调）。
  - 未选原因：服务内调用更高效、类型安全更好、错误处理更可控。

### 2) 使用统一 mutation 包装器触发净值

- 决策：提供 `runMutationWithNetvalue(userId, action)`（命名可调整），在包装器内执行主业务并在成功后触发 `recordTodayNetvalue`。
- 原因：比“每个接口末尾手写一行”更可维护，降低未来漏挂风险。
- 备选方案：手动在每个路由末尾调用。
  - 未选原因：变更扩散、易遗漏、回归风险高。

### 3) 时区配置复用 `settings`，键名 `netvalue.timezone`

- 决策：新增用户设置键 `netvalue.timezone`；读取不到时使用默认 `Asia/Shanghai`。
- 原因：无需 schema 迁移，符合现有 settings 结构。
- 备选方案：在 users 表新增 timezone 字段。
  - 未选原因：需要迁移与双数据库兼容改造，当前收益不高。

### 4) “当日”日期按用户时区计算

- 决策：通过 `Intl.DateTimeFormat('en-CA', { timeZone })` 等方式稳定得到 `YYYY-MM-DD` 业务日期，并统一用于 netvalue upsert 的 `date`。
- 原因：确保跨时区用户按本地日切换，不受服务器时区影响。
- 备选方案：继续用 `toISOString().slice(0, 10)`。
  - 未选原因：这是 UTC 日期，无法满足用户时区语义。

### 5) 每日自动记录采用 cron + 用户本地 03:00 窗口

- 决策：新增受密钥保护的 `POST /api/cron/netvalue`，按小时运行；任务内按每个用户时区判断当前是否处于 03:00 窗口，命中则执行当日记录。
- 原因：平台定时通常基于单一时区，无法直接为每个用户精确配置不同时区的 03:00；“小时级扫描 + 本地时间判断”实现简单且稳定。
- 备选方案：单次每日（服务器时区）cron。
  - 未选原因：不能满足“按用户时区凌晨 3 点”要求。

### 6) 写入策略使用原子 upsert

- 决策：对 `(userId, date)` 采用数据库原子 upsert（SQLite/PG 均支持），同日多触发只更新不新增。
- 原因：并发安全，避免先查后写导致竞态。
- 备选方案：先 select 再 insert/update。
  - 未选原因：存在并发窗口与重复逻辑。

## Risks / Trade-offs

- [定时任务频率提升导致额外计算开销] → 仅对命中 03:00 窗口的用户执行；可增加最近执行标记避免同小时重复。
- [部分 mutation 成功后净值更新失败] → 包装器中净值更新失败不回滚主交易，记录错误日志并由 cron 补偿。
- [时区值非法导致日期计算异常] → 设置写入时校验 IANA 时区；读取异常时回退 `Asia/Shanghai`。
- [跨数据库 upsert 语法差异] → 使用 Drizzle 统一 API 封装并补充 SQLite/PG 双模式验证。

## Migration Plan

1. 提交设计与 specs 后进入实现。
2. 先落地净值服务与包装器，再替换各 mutation 接口调用。
3. 移除 Dashboard 手动按钮，保留现有页面加载自动触发能力。
4. 增加设置项 `netvalue.timezone` 的读写与默认值回退。
5. 新增 cron 路由与部署配置（本地与云端各自接入计划任务）。
6. 回归验证：写操作联动、时区日期、定时触发、同日幂等。

回滚策略：

- 保留 `/api/netvalue` 现有入口可快速退回“仅页面触发”；若 cron 异常可先下线 cron 路由而不影响主业务。
