## Context

当前 `POST /api/holdings/fetch-prices` 的自动报价逻辑以市场后缀分发数据源，但港股/A股在生产使用中暴露出三个问题：

1. 单一供应商覆盖与权限不稳定，导致更新失败率高。
2. 代码映射兼容不足（A股后缀、Stooq 特殊符号），存在“有数据但格式不命中”的失败。
3. 前端仅显示摘要，不显示逐条原因，用户无法快速判断是未配置 API Key、供应商权限、限流还是代码格式问题。

本次设计覆盖后端数据源路由、用户级 API Key 设置、以及 Dashboard/Batch Update 的结果展示交互。

## Goals / Non-Goals

**Goals:**

- 在保持美股/日股现有 Stooq 逻辑不变的前提下，为港股/A股引入 `Twelve Data` 主 + `EODHD` 备回退链路。
- 新增用户级供应商 API Key 配置（Twelve Data / EODHD），由设置接口读写。
- 增强代码兼容映射（`.SS/.SZ/.HK` 与 `BRK.B.US` 等）。
- 报价结果改为逐条可视化明细，成功项显示最新价与数据来源，失败项显示具体错误。

**Non-Goals:**

- 不改动交易、持仓编辑、净值计算等非报价链路。
- 不引入新的数据库表，继续复用 `settings` 键值存储。
- 不承诺 Twelve Data 免费计划可覆盖全部 A股/港股标的（该项由供应商套餐能力决定）。

## Decisions

1. 数据源路由策略

- 美股/日股：继续走 Stooq，避免影响现有稳定路径。
- 港股/A股：优先 Twelve Data，失败后回退 EODHD。
- 理由：满足“主备供应商”要求，同时最小化对已稳定市场的回归风险。
- 备选方案：全部市场统一迁移到单一供应商。放弃原因：迁移面过大且会引入不必要风险。

2. Twelve Data 批量限流策略

- 港股/A股请求按 8 条/批，批次间隔 65 秒。
- 理由：贴合供应商分钟级限额约束，降低批量请求被限流概率。
- 备选方案：并发一次性请求。放弃原因：高概率触发限频并导致整批失败。

3. 代码映射与回退候选

- A股使用多候选格式尝试（如 `601088.SSE`、`601088 + exchange=SSE` 等）。
- Stooq 增加符号兼容转换（如 `BRK.B.US -> brk-b.us`）。
- 理由：不同供应商对 symbol 格式要求差异大，需要兼容层避免无效失败。

4. 失败错误透传

- 在 `failed.error` 中透传供应商原始错误（包含权限/套餐提示）。
- 理由：统一“无数据”会误导用户；透传可快速定位为配置、权限或格式问题。

5. 前端结果交互改造

- Dashboard 与 Batch Update 统一使用结果弹窗组件，逐条展示更新结果。
- 理由：跨页面行为一致，用户无需打开 Network 面板即可排查问题。

## Risks / Trade-offs

- [Twelve Data 部分市场需更高套餐] → 通过错误透传明确提示，并提供 EODHD 备援配置路径。
- [批次间隔导致一次更新耗时上升] → 仅对港股/A股应用该策略，且以成功率优先。
- [多候选映射增加维护成本] → 将映射逻辑集中在单一路由与适配层，避免分散实现。
- [前后端返回字段扩展影响兼容] → 保持 `updated/failed/skipped` 顶层结构不变，仅扩展 `updated` 字段。
