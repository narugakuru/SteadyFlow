## Context

本次变更横跨前端弹窗交互与后端同步链路。

- `src/components/discipline-notes-fab.tsx` 当前只约束了弹窗宽度，没有为阅读态与编辑态提供统一的高度骨架；`article` 与 `textarea` 各自使用独立的最小高度，导致切换模式时弹窗主体尺寸和滚动位置都会变化。保存动作依赖底部显式按钮，不符合“失焦即保存”的目标。
- 当前笔记弹窗把列表、标题、正文、底部操作与提示语放在同一自然文档流中，正文滚动时更容易推动整个弹窗内容，而不是仅在正文框内部滚动。
- `POST /api/holdings/fetch-prices` 当前直接调用 `syncHoldingPricesForUser()`；只有在 `updated.length > 0` 时才会通过 `runMutationWithNetvalue()` 触发净值重算。汇率刷新因此是净值链路的间接副作用，而不是报价同步 API 的显式步骤，导致“无成功报价更新”或“只想刷新价格/汇率”的请求无法可靠刷新汇率。
- 每日 Cron 当前会先跑报价同步再记净值，但报价同步服务本身并未承担“同步检查汇率缓存”的职责，行为契约不够集中。

该变更需要在不改数据模型、不新增外部依赖的前提下，把笔记弹窗稳定性与报价+汇率一致性收敛到现有模块里。

## Goals / Non-Goals

**Goals:**

- 让投资笔记弹窗在桌面端阅读/编辑模式下保持同一套大尺寸骨架，移动端占满可视区域。
- 让正文滚动发生在正文框内部，避免整个弹窗主体随着长文本上下移动。
- 移除笔记显式保存按钮，改为失焦自动保存，同时避免因为模式切换或关闭弹窗造成内容丢失。
- 让 manual、silent-client、cron 三类报价同步都显式复用汇率刷新逻辑，并继续沿用现有缓存/降级规则。

**Non-Goals:**

- 不重做笔记中心的信息架构、数据库字段或 Markdown 渲染能力。
- 不改变报价供应商优先级、返回结构主形态或 `quote_sync.*` 元数据模型。
- 不引入新的富文本编辑器、状态管理库或后台任务系统。

## Decisions

### Decision 1: 用固定高度的弹窗骨架承载笔记列表与正文区

桌面端笔记中心改为基于视口高度的固定骨架，例如“最大宽度 + 固定/上限高度 + 内部 flex 布局”；移动端切到全屏式 Dialog，使用 `100dvh` 和安全区内边距。阅读态与编辑态共享同一个正文容器尺寸，只替换容器内部的渲染节点，而不是让整个弹窗跟着节点高度变化。

理由：用户反馈的“UI 大小跳动”本质上是容器骨架不稳定，而不是单一控件高度不足。先稳定外层骨架，阅读/编辑两态才有一致的空间感。

备选方案：仅分别调大 `article` 和 `textarea` 的 `min-height`。未采用，因为外层仍会随着内容自然撑开，移动端也无法直接获得全屏行为。

### Decision 2: 把滚动职责收敛到便签列表和正文容器内部

弹窗外层内容区使用 `overflow-hidden`，左侧便签列表和右侧正文区各自成为可滚动子容器；正文阅读框与编辑框复用同一个带边框的内容槽，滚动条位于内容槽内部。标题、经典句子、删除操作等外围元素保持固定，不参与正文滚动。

理由：用户描述中的“进度条应该包含在文本框内部”本质上是在要求滚动条属于文本容器，而不是整个模态层。将滚动边界内聚后，长文阅读和编辑时只有正文在动。

备选方案：继续让 `DialogContent` 自身滚动。未采用，因为这会让标题、列表、按钮、提示语都跟着位移，交互焦点不稳定。

### Decision 3: 自动保存以“离开当前笔记编辑上下文”为触发点，而不是保留显式保存按钮

删除底部“保存笔记”按钮，保留创建/删除操作。组件维护“当前草稿”和“上次已保存快照”两份状态；当用户离开当前笔记编辑上下文时触发保存，包括：

- 从正文编辑态回到阅读态
- 切换到另一条笔记
- 关闭弹窗
- 焦点整体离开当前笔记编辑区域

保存前先做 dirty-check，未变化则不请求；保存失败时保留草稿并提示错误。

理由：单纯对每个输入框做原始 `blur` 保存会在标题框和正文框之间切换时产生过多请求，而“离开当前笔记编辑上下文”既符合用户“失焦自动保存”的直觉，也能降低噪音请求。

备选方案：改为 debounce 自动保存。未采用，因为用户明确要求“失去焦点自动保存”，而不是持续输入时后台频繁提交。

### Decision 4: 在报价同步核心服务中显式调用汇率刷新，而不是继续依赖净值副作用

`syncHoldingPricesForUser()` 在处理 holdings 前后显式调用 `getExchangeRates()`，把“检查并刷新当日汇率缓存”纳入报价同步核心流程。该调用对 `manual`、`silent-client`、`cron` 三种触发来源一视同仁；即使没有任何持仓成功更新，也必须执行这一步。由于 `getExchangeRates()` 已内置“当日缓存直接复用、过期才外部拉取、失败回退旧缓存/默认值”的语义，因此无需新增表或设置键。

理由：汇率刷新应该成为报价同步 API 的显式契约，否则“无 updated 项就不刷新汇率”的现象会持续存在，且行为散落在 route 与 netvalue side effect 之间。

备选方案：继续依赖 `runMutationWithNetvalue()` 或在前端单独调用 `/api/exchange-rates`。未采用，因为前者只在部分路径触发，后者会把一致性责任推回调用方。

### Decision 5: 保持现有报价接口主返回结构不变

`POST /api/holdings/fetch-prices` 继续返回 `updated`、`failed`、`skipped` 主结构，不额外引入强制的新响应字段；汇率刷新作为同请求内的保证性副作用处理。后续资产汇总、净值记录、Dashboard 汇率展示通过现有读取链路获得更新后的汇率。

理由：本次需求重点是让 API 行为更完整，而不是改造前后端契约。保持结果弹窗兼容，可降低实现面和回归面。

备选方案：在响应中新增 `exchangeRate` 状态块。未采用，因为当前 UI 无展示需求，且会扩大调用方改造范围。

## Risks / Trade-offs

- [自动保存触发点判断过宽，可能产生重复请求] → 通过 dirty-check 和“编辑上下文级别”触发收敛请求次数。
- [移动端全屏弹窗可能改变现有关闭手势与视觉密度] → 保持现有 Dialog 行为，只调整尺寸与内部布局，不改变入口和核心操作。
- [把汇率刷新纳入报价同步会增加部分请求耗时] → 复用现有日级缓存；大多数当天内请求直接命中缓存，不触发外部调用。
- [汇率 API 失败可能让用户误以为本次同步完全失败] → 保持报价结果返回不受阻断，并继续沿用 stale cache/default 降级语义。
- [关闭弹窗或切换笔记时触发保存，可能与并发中的保存请求冲突] → 以 noteId + last-saved snapshot 做幂等保护，后发请求只在草稿仍匹配当前 note 时落地 UI。

## Migration Plan

1. 先更新 `discipline-notes`、`auto-quote-fetch`、`exchange-rate` 的 delta specs，明确行为契约。
2. 重构笔记弹窗布局为固定高度骨架，拆分列表滚动区与正文滚动区，移除显式保存按钮并接入自动保存。
3. 在报价同步服务中显式调用汇率刷新逻辑，并验证 manual/silent-client/cron 三条链路共用同一行为。
4. 回归验证桌面与移动端笔记弹窗、无报价更新场景下的汇率刷新、以及 Cron 链路在汇率降级时仍可继续记录净值。

回滚策略：若自动保存或全屏弹窗出现明显回归，可先回退前端笔记组件改动，恢复显式保存按钮；若报价同步联动汇率出现异常，可回退服务层显式调用，暂时恢复现有净值副作用路径。两部分互相独立，不涉及数据迁移。

## Open Questions

- 自动保存失败时是否需要增加更明显的“未保存”状态提示，而不只是错误文案。
- 移动端全屏笔记弹窗是否需要额外的顶部关闭栏或返回手势提示，以适配窄屏场景。
