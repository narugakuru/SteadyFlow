## Context

当前前端页面大多在组件挂载后直接请求 API，并在请求期间显示全页 Loading，导致用户在登录后与路由切换时有明显等待。代码层面缺少统一查询缓存抽象，不同页面和组件重复请求 `/api/accounts`、`/api/holdings`、`/api/asset-allocation` 等接口。

本次变更需要在不改变后端 API 契约的前提下，建立统一的客户端缓存层，满足以下约束：

- 用户体验优先：命中缓存时立即展示，避免“白屏等待”。
- 一致性可控：通过统一失效映射保证写后读正确性。
- 安全隔离：多用户会话下缓存按 `userId` 分区，避免串数据。
- 维护性：所有缓存时效与刷新规则集中配置。

## Goals / Non-Goals

**Goals:**

- 为核心业务页提供统一的“缓存优先 + 条件异步刷新”读取模式。
- 统一缓存策略配置，固定为 `staleTime=60s`、`persistTime=3d`。
- 当缓存年龄 `<=60s` 时仅使用缓存，不触发异步远端刷新。
- 当缓存年龄 `>60s 且 <3d` 时先展示缓存，再异步刷新并无刷新页面地更新数值。
- 提供全局“后台刷新失败”通知条，显示后缓慢自动消失。
- 在页面不显眼位置以小字号显示数据新鲜度。
- 建立统一 mutation 失效映射与跨标签页同步机制。

**Non-Goals:**

- 不调整后端 API 字段结构和业务含义。
- 不在本次变更中引入离线写入与冲突合并。
- 不改变市场数据来源或计算口径。
- 不将通知条升级为重型消息中心（仅处理后台刷新失败提示）。

## Decisions

### 1) 使用查询缓存库 + IndexedDB 持久化，而非页面级手写缓存

- Decision:
  - 引入统一客户端查询层（如 TanStack Query）并启用 IndexedDB 持久化插件。
  - 缓存架构采用两级：L1 内存（会话内）+ L2 IndexedDB（跨刷新）。
- Rationale:
  - 现有页面请求分散，手写缓存容易出现策略漂移和失效遗漏。
  - 查询库天然支持 stale/fresh、后台刷新、invalidation、并发去重。
  - IndexedDB 更适合 3 天持久化和较大数据量（交易/净值历史）。
- Alternatives considered:
  - 仅 `localStorage`：容量和序列化性能风险较高，难以长期稳定。
  - 完全自研 query 缓存：维护成本高、易产生竞态和一致性缺陷。

### 2) 统一策略文件集中维护

- Decision:
  - 新增统一策略配置（如 `src/lib/cache/policy.ts`），集中定义每个 query 的 key、时效、刷新触发、失效依赖和优先级。
  - 默认策略统一为 `staleTime=60_000`、`persistTime=259_200_000`（3 天）。
- Rationale:
  - 避免策略散落在页面组件中，降低后续维护成本。
  - 便于审计“哪些写操作会影响哪些读缓存”。
- Alternatives considered:
  - 页面各自配置：短期快、长期不可控。

### 3) 刷新判定规则采用“缓存年龄门槛”而非固定每次重拉

- Decision:
  - 使用缓存记录时间戳 `cachedAt` 计算年龄。
  - `age <= 60s`：直接返回缓存，不发后台请求。
  - `60s < age < 3d`：返回缓存并触发后台刷新。
  - `age >= 3d`：视为持久化失效，不读取该缓存并走远端请求。
- Rationale:
  - 满足用户对“快速展示优先”的诉求，同时避免 60 秒内重复请求。

### 4) 全局刷新失败通知条 + 低侵入新鲜度文案

- Decision:
  - 提供全局 `SyncBanner` 组件，后台刷新失败时展示，自动缓慢淡出。
  - 页面展示“数据更新于 xx 秒前/xx 分钟前”小字号文案，放在不显眼位置。
- Rationale:
  - 用户可感知“当前是缓存视图且刷新失败”，但不被高频打扰。
  - 与投资场景匹配：大多数页面并非高频秒级交易面板。
- Alternatives considered:
  - Modal/Alert 弹窗：打断操作，不适合后台刷新失败。
  - 完全不提示：用户无法判断是否已更新。

### 5) 用户隔离、401 清理与跨标签页同步

- Decision:
  - 所有缓存 key 必须带 `userId` 分区（如 `im:v1:${userId}:${queryKey}`）。
  - 登出与 401 时清理当前用户缓存。
  - 使用 `BroadcastChannel` 广播失效事件，保持多标签页一致。
- Rationale:
  - 防止多账号切换后的脏数据显示与隐私风险。
  - 保证写操作在多个标签页下的可见一致性。

## Risks / Trade-offs

- [缓存与服务端短暂不一致] → 通过小字号新鲜度与失败通知条提示状态，写后主动失效关键 query。
- [失效映射遗漏导致旧数据停留] → 维护集中 `mutationInvalidates` 映射并在评审中检查。
- [跨标签页广播噪声或风暴] → 广播事件去重与节流，仅发送 query key 级别失效信号。
- [IndexedDB 存储膨胀] → 按 `persistTime=3d` 自动过期，必要时按 query 大小与数量加上限清理。
- [新增依赖引入学习成本] → 通过统一封装 hook 屏蔽库细节，页面按约定使用。

## Migration Plan

1. 引入查询缓存与 IndexedDB 持久化基础设施，接入应用根布局 Provider。
2. 建立统一策略文件，落地固定的 60s/3d 规则与失效映射。
3. 先迁移 Dashboard 验证“缓存优先 + 条件刷新 + 失败通知条”闭环。
4. 迁移 Accounts、Transactions、Batch Update、Netvalue、Market、Admin 页面数据读取。
5. 将关键写操作接入统一 invalidation，并补充跨标签页同步。
6. 灰度验证后移除旧的页面级 `setLoading(true)+直接 fetch` 模式。

Rollback strategy:

- 保留旧请求路径开关（按页面或全局 flag 回退到直接请求模式）。
- 若出现一致性问题，可临时关闭持久化，仅保留内存缓存。

## Open Questions

- 市场页是否继续完全复用 60s 规则，还是后续单独放宽（当前先按统一策略执行）。
- 首次冷启动无缓存且网络失败时，是否需要“上次过期缓存只读兜底”模式（本次先不启用）。
