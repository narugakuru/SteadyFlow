## Context

当前免费版部署约束下，Cron 仅能每日一次触发，且函数执行有时长上限。若每日净值任务不先同步股价，会导致净值使用旧价格；若一次任务全量串行所有用户，可能因超时导致整批失败。需要把每日任务升级为“先价后值”的编排流程，并在时间预算内保证部分用户可成功更新。

## Goals / Non-Goals

**Goals:**

- 每日 Cron 对每个用户执行“先自动更新股价，再写入当日净值”。
- 采用宽松模式：股价更新部分失败仍可写净值，同时记录报价同步状态。
- 支持按用户分批执行与游标续跑，确保超时场景下至少部分用户成功。
- 输出可观测执行结果，支持后续补偿重跑。

**Non-Goals:**

- 不改造股价更新的供应商选择策略（主备与映射规则沿用现有实现）。
- 不改造净值图表展示与前端交互。
- 不引入消息队列或外部任务系统。

## Decisions

1. Cron 编排顺序固定为“先价后值”

- 决策：在每日 Cron 内部以用户为单位，先执行该用户报价更新，再执行净值写入。
- 原因：确保净值快照尽量基于当次最新价格。
- 备选：先写净值再更新股价。放弃原因：会稳定产生滞后净值。

2. 宽松模式落库策略

- 决策：无论报价结果为 `ok/partial/failed`，均执行当日净值 upsert；同时写入/返回报价同步状态与统计。
- 原因：优先保证“当天有净值记录”，避免因单个供应商异常导致整日缺失。
- 备选：严格模式（报价失败不写净值）。放弃原因：会放大外部数据源抖动对业务连续性的影响。

3. 用户分批与时间预算

- 决策：按用户批次执行（例如每批 N 个），每处理完一个用户立即落库；接近超时时提前停止并返回未处理游标。
- 原因：即使任务中断，也能保证已处理用户结果持久化。
- 备选：全量单批串行。放弃原因：超时风险高且失败面大。

4. 游标续跑机制

- 决策：在 `settings` 或专用状态键保存最近处理游标（如上次用户索引/ID），下次 Cron 从游标继续，循环覆盖所有用户。
- 原因：每日一次触发下，避免总是从头开始导致尾部用户长期饥饿。

## Risks / Trade-offs

- [部分用户当日仍可能未处理（遇到超时）] → 通过游标续跑保证后续周期覆盖，并在响应中暴露未处理数量。
- [宽松模式会写入“报价未完全同步”的净值] → 记录 `quoteSyncStatus`，在后续分析/排障中可区分数据质量。
- [批次过大触发超时，过小导致吞吐不足] → 参数化批次大小与剩余时间阈值，按运行数据迭代调整。
- [Cron 触发时间漂移] → 业务定义按“触发时用户本地当天”记账，不依赖精确时刻。

## Migration Plan

1. 抽取可复用“按用户执行报价更新”的服务函数，供 Cron 内部直接调用。
2. 改造 `/api/cron/netvalue` 为用户分批编排，接入时间预算中断与游标更新。
3. 在净值记录结果中附带报价同步状态（ok/partial/failed）与统计字段。
4. 回归验证：少量用户、多用户、超时中断、次日游标续跑、报价失败场景。
5. 上线后观察 7 天执行日志，按成功率调整批次参数。

## Open Questions

- `quoteSyncStatus` 仅写入 cron 返回，还是需要持久化进 netvalue `dataJson` 供历史追踪？
