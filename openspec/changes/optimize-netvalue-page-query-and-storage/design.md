## Context

当前净值页通过单一 `GET /api/netvalue` 返回当前用户全部净值记录，前端同时用这份全量结果驱动历史列表和两张图表。该设计在记录天数持续增加后会同时放大三类成本：

- 传输成本：列表翻页与图表区间查询都必须携带整段历史数据。
- 渲染成本：前端在页面内同时排序、遍历和聚合全部记录。
- 存储成本：`netvalue.dataJson` 仍保留净值页未直接消费的 `accounts` 快照，长期占用 Neon 免费版有限空间。

现有客户端缓存层已经支持参数化 query key 和写后失效，但净值页仍只使用单个 `netvalue` 查询名，无法把列表分页和图表区间作为两个独立缓存对象处理。与此同时，`netvalue` 表在 SQLite 与 PostgreSQL 双方言下都只有一个 `dataJson` 文本列，因此本次数据结构收缩需要兼顾新旧快照兼容和历史回填。

## Goals / Non-Goals

**Goals:**

- 将净值历史列表与净值图表拆成两个独立读取契约，分别服务分页与区间图表场景。
- 为净值图表定义固定的 `range -> grain` 映射，并在服务端按周/月返回期末值。
- 将净值相关客户端缓存拆成 `netvalue-list` 与 `netvalue-chart` 两类参数化键，并统一提升到 `staleTime=60m`。
- 精简新写入的 `netvalue.dataJson` 结构，仅保留 `allocation` 与 `rates`，并提供安全的历史迁移路径。

**Non-Goals:**

- 不在本次 change 内引入新的聚合表、物化视图或第三方缓存层。
- 不在本次 change 内提供用户可配置的自定义粒度切换；粒度仅由固定区间映射决定。
- 不在本次 change 内改变净值记录的写入频率，仍沿用“写操作触发 + 每日 Cron 保底”的现有机制。
- 不在本次 change 内重放交易历史重新计算多年净值；长周期图表只基于已落库的 `netvalue` 日快照。

## Decisions

### 1. 净值读取拆为 `/api/netvalue/list` 与 `/api/netvalue/chart`

**选择**

- 新增 `GET /api/netvalue/list?page=<n>&pageSize=<m>`，专用于历史列表。
- 新增 `GET /api/netvalue/chart?range=<30d|90d|1y|3y|all>`，由服务端根据固定映射决定 `grain`，并在响应中回传实际 `grain`。
- 原有全量 `GET /api/netvalue` 读取契约不再作为净值页主读取入口。

**原因**

- 列表和图表的查询维度不同：列表关心分页，图表关心区间与聚合粒度，继续共用一个接口会让两边都过度取数。
- 分开后，浏览器缓存、失效策略和 UI 状态管理都更清晰。
- `chart` 接口回传实际 `grain` 可以让前端 tooltip、X 轴标签和空态逻辑与服务端保持一致。

**备选方案**

- 在单个 `/api/netvalue` 下通过 `mode=list|chart` 切分：接口路径更少，但契约会持续膨胀。
- 保持单接口全量返回，由前端自行分页和聚合：实现最省，但正是本次要解决的问题。

### 2. 图表聚合完全放在服务端，周/月都取“该周期最后一个可用净值”

**选择**

- 固定映射：
  - `30d -> day`
  - `90d -> day`
  - `1y -> week`
  - `3y -> month`
  - `all -> month`
- `day` 直接返回区间内日净值。
- `week` 与 `month` 不做平均值，统一返回该周期最后一条可用净值记录的 `totalAssetCny` 与 `allocation`。
- 周聚合按 ISO 周处理，即周一开周；若周期结束日无记录，取该周期内最后一个可用记录。

**原因**

- 投资场景下，总资产与仓位结构更适合看“期末状态”，而不是周期平均值。
- 前端不需要再拉取全年日级数据后自行压缩，避免重复计算。
- 5 年日快照量级约为千级行数/用户，直接按用户 + 日期范围读取后在服务端聚合，计算量足够小，不需要额外数据库缓存层。

**备选方案**

- 周/月取平均值：更适合统计口径，但会扭曲资产占比的投资语义。
- 完全依赖 SQL `date_trunc` 聚合：总资产可行，但 `allocation` 仍需要“取周期最后一条记录”，实现并不会更简单。
- 增加用户可选粒度：灵活但会抬高 UI、缓存键和测试复杂度。

### 3. `netvalue.dataJson` 改为瘦身写入，读取层同时兼容新旧结构

**选择**

- 新写入与同日 upsert 后的 `dataJson` 仅包含：
  - `allocation`
  - `rates`
- 历史旧记录允许继续带有 `accounts` 字段；读取层必须忽略未知字段，并把新旧结构统一标准化后再返回给列表/图表接口。
- 提供一个批量回填脚本或迁移任务，把历史记录中的 `accounts` 剥离掉，降低长期存储占用。

**原因**

- 当前净值页的列表与图表都不消费 `accounts`；继续保留只会扩大载荷和存储。
- 先做读兼容，再做历史回填，可以把发布风险降到最低。
- 保留 `rates` 有利于后续净值调试与历史汇率口径追查。

**备选方案**

- 只改新写入，不处理历史数据：风险最低，但难以真正回收已有存储。
- 一次性 SQL 迁移直接改写所有历史行：节省代码兼容时间，但回滚与中断恢复更脆弱。
- 新增独立 JSONB/子表拆分结构：长期更干净，但超出本次必要复杂度。

### 4. 净值缓存拆为两个查询名，并为二者设置 `60m` stale override

**选择**

- 客户端缓存层新增：
  - `netvalue-list`
  - `netvalue-chart`
- `netvalue-list` 的 query key 参数至少包含 `page` 与 `pageSize`。
- `netvalue-chart` 的 query key 参数至少包含 `range` 与 `grain`。
- 这两类查询统一使用 `staleTime=60m`、`persistTime=3d`。
- 所有会触发净值更新的写操作继续统一失效净值相关查询，但失效目标改为这两个新 scope。

**原因**

- 列表翻页和图表切区间本质上是不同缓存对象，必须解耦。
- 净值历史变化频率低，且写操作完成后会主动失效，`60m` stale 能显著减少无意义后台刷新。
- 复用现有参数序列化与跨标签页失效框架，不需要重做缓存基础设施。

**备选方案**

- 继续沿用 `netvalue` 单 query name：会让分页和图区间互相污染缓存。
- 把 netvalue 查询也维持全局 `60s` stale：数据更“新”，但对历史查询收益很低。

## Risks / Trade-offs

- [历史回填进行到一半时存在新旧结构混合] → 读取层先兼容新旧结构，回填任务按批执行且支持重复运行。
- [图表接口区间聚合规则实现不一致导致总资产与占比曲线错位] → 周/月统一基于同一条“期末快照”产出两个图表的数据。
- [列表与图表拆接口后前端状态管理更复杂] → 用独立 query key、独立 loading/error 状态，避免一个请求影响另一块 UI。
- [Neon/Serverless 冷启动带来首个图表请求延迟] → 历史净值是低频读场景，可接受；同时通过 `60m` stale 和 3 天持久化降低重复命中概率。
- [历史回填脚本占用免费额度] → 单用户 5 年日快照量级较小，按批分页更新即可，避免长事务与全表锁定。

## Migration Plan

1. 先上线读取兼容层，使列表与图表都能读取带 `accounts` 的旧结构和瘦身后的新结构。
2. 新增 `/api/netvalue/list` 与 `/api/netvalue/chart`，并让净值页改用新接口；原全量读取接口在过渡期内保留但不再作为页面主路径。
3. 更新 `recordTodayNetvalue` 写入逻辑，后续新记录与同日覆盖记录只写入 `allocation + rates`。
4. 将客户端缓存 query name 拆分为 `netvalue-list` 与 `netvalue-chart`，并同步修改写后失效映射。
5. 提供历史 `netvalue.dataJson` 回填任务，按批删除旧记录中的 `accounts` 字段。
6. 观察线上一段时间后，再决定是否彻底移除旧全量读取接口。

**Rollback**

- 若新列表或图表接口出现问题，可先切回旧读取入口，因为读取兼容层仍支持旧结构。
- 若历史回填任务中断，不影响功能正确性；旧记录继续可读，后续可重试未完成批次。
